# Базовый протокол GUI v1

## Назначение

Этот документ задаёт общие правила IPC для `displayserv`, `compositorserv`,
`windowserv` и клиентских GUI-библиотек. Специализированные протоколы определяют
свои `message_type` и предметные поля, но используют описанные здесь транспорт,
кодирование, корреляцию запросов, ошибки и правила владения.

## Уровни протокола

```text
Предметное сообщение GUI
  └── payload GUI-протокола
        └── кадр ipclib: payload_size + message_type + payload
              └── локальный Unix domain socket
```

`ipclib` отвечает за границы кадров и доставку байтов. GUI-протокол отвечает за
смысл `message_type` и содержимое payload. Поля `payload_size` и `message_type`
не дублируются внутри GUI payload.

Один кадр `ipclib` содержит ровно одно GUI-сообщение. Объединять несколько
GUI-сообщений в один payload или разделять одно сообщение между кадрами нельзя.

## Кодирование

1. Все целые значения кодируются в little-endian.
2. Поля записываются последовательно без неявного выравнивания и padding.
3. C/C++-структуры нельзя отправлять через копирование их памяти: padding,
   размер enum и представление указателей не являются частью wire format.
4. Знаковые числа используют дополнительный код фиксированной разрядности.
5. `bool` кодируется как `u8`: `0` означает `false`, `1` означает `true`.
   Остальные значения недопустимы.
6. Enum кодируется как `u32`, если специализированный протокол явно не задаёт
   другую ширину.
7. Идентификаторы и serial кодируются как `u64`; значение `0` недействительно,
   кроме полей, где специализированный протокол явно использует его как `none`.
8. Строка кодируется как `u16 byte_length` и `u8 bytes[byte_length]`. Байты
   должны образовывать корректный UTF-8 без завершающего `NUL`.
9. Массив кодируется счётчиком фиксированной ширины, после которого элементы
   идут подряд. Получатель проверяет счётчик до вычисления полного размера.
10. Неизвестные trailing bytes запрещены в v1, если конкретное сообщение не
    объявляет расширяемый хвост.

Максимальный payload ограничен `IPC_MESSAGE_MAX_SIZE`. Специализированный
протокол обязан задавать более строгие пределы для строк, массивов и регионов.

## Категории сообщений

| Категория | Направление | Назначение |
| --- | --- | --- |
| Request | Клиент → сервис | Запрос операции или изменение pending state |
| Result | Сервис → клиент | Результат конкретного запроса |
| Event | Сервис → клиент | Асинхронное изменение состояния или завершение работы |

Каждый `message_type` принадлежит протоколу одного endpoint. Одинаковое число
может иметь другой смысл у другого сервиса. В рамках одного endpoint номер и
направление сообщения после публикации версии изменять нельзя.

## Запрос

Каждый request payload начинается с `RequestPrefix`:

| Смещение | Поле | Тип | Ограничение |
| --- | --- | --- | --- |
| `0` | `protocol_version` | `u16` | Для этой версии равно `1` |
| `2` | `request_id` | `u64` | Ненулевой и уникальный среди незавершённых запросов соединения |
| `10` | предметные поля | зависит от сообщения | Определяются специализированным протоколом |

`RequestPrefix` занимает 10 байт. Реализация читает поля по смещениям и не
приводит указатель на payload к нативной структуре.

Клиент выбирает `request_id`. После финального result значение можно
использовать повторно; если операция предусматривает completion event — только
после этого события. Монотонный счётчик предпочтителен. Сервис возвращает тот
же `request_id` и не изменяет его.

Однонаправленные запросы также содержат `RequestPrefix`. Их предметные ошибки
возвращаются ближайшим синхронизирующим result, если это прямо установлено
специализированным протоколом; нарушение wire format разрывает соединение.

## Ответ

Обычный result payload начинается с `ResultPrefix`:

| Смещение | Поле | Тип | Ограничение |
| --- | --- | --- | --- |
| `0` | `error` | `u32` | Числовое значение `ErrorCode` из `libcore` |
| `4` | `request_id` | `u64` | Равен идентификатору запроса |
| `12` | данные результата | зависит от сообщения | Определены только при разрешающем их `ErrorCode` |

`ResultPrefix` занимает 12 байт. `CORE_OK` является единственным успешным
результатом. При ошибке сервис не создаёт объект и не оставляет частично
применённое состояние, если специализированный протокол явно не описывает
иначе.

Числовые значения `ErrorCode` должны быть закреплены системным ABI как `u32`
до реализации wire-кодека. GUI-протокол не назначает собственные номера
системным ошибкам; изменение номера после его публикации нарушает ABI.

Каждый запрос, для которого заявлен result, получает ровно один result. При
закрытии соединения незавершённые запросы считаются отменёнными и отдельные
ответы не отправляются.

## События

Событие не является ответом и может прийти между result других запросов.
События изменения состояния содержат `Serial` в позиции, заданной их схемой.
Serial монотонно возрастает в области, которую определяет специализированный
протокол: соединение, объект или источник ввода.

Completion event асинхронной операции повторяет её `request_id`. Например,
успешный `display.present_result` означает постановку кадра в очередь, а
`display.presented` или `display.present_failed` с тем же `request_id` сообщает
финальный результат показа.

Клиент не предполагает, что события разных соединений имеют общий порядок.
Внутри одного соединения сервис ставит сообщения в очередь в причинном
порядке: result создания объекта предшествует событиям этого объекта, а
событие удаления является последним для его идентификатора.

## Версионирование

- Каждый запрос указывает версию предметного протокола.
- В v1 нет отдельного handshake: версия принимается при разборе запроса.
- Result кодируется по версии соответствующего запроса.
- События подписки кодируются по версии запроса, создавшего подписку.
- Неподдерживаемая версия возвращает `CORE_UNSUPPORTED`, если request prefix
  и result для этого `message_type` можно безопасно разобрать.
- Добавление необязательного поля в существующий payload считается изменением
  версии. Новый `message_type` можно добавить в следующей версии без изменения
  уже опубликованных номеров.

## Файловые дескрипторы

Сообщение может нести ancillary FD только тогда, когда его схема задаёт точное
число FD. Лишний или отсутствующий FD является нарушением протокола.

Отправитель сохраняет свой исходный FD. Получатель получает отдельную копию и:

1. проверяет число FD и payload;
2. проверяет метаданные и размер backing storage;
3. принимает копию FD во владение только после успешного импорта;
4. закрывает каждую непотреблённую копию при любой ошибке или disconnect.

Текущий контракт `ipclib` использует `send()`/`recv()` и ещё не предоставляет
ancillary data. Поэтому `buffer.import` и `display.present` нельзя реализовать
по целевому протоколу до добавления ограниченной передачи FD через
`sendmsg()`/`recvmsg()`. Формат GUI-сообщений уже фиксирует требуемое число FD,
но не объявляет копирование пикселей через payload публичной альтернативой.

## Владение объектами

- Созданный объект принадлежит IPC-соединению, если протокол явно не назначает
  другого владельца.
- Клиент не может обращаться к идентификатору другого соединения.
- `destroy` делает идентификатор недействительным для новых запросов.
- Disconnect уничтожает объекты соединения, отменяет подписки и освобождает
  принятые FD без дополнительных запросов клиента.
- Перезапуск сервиса инвалидирует выданные им идентификаторы и serial.
- Передача числового идентификатора не передаёт владение объектом.

## Ошибки протокола

| Ситуация | Действие сервиса |
| --- | --- |
| Корректный запрос с предметной ошибкой | Вернуть result с подходящим `ErrorCode` |
| Неподдерживаемая версия | Вернуть `CORE_UNSUPPORTED`, если возможен безопасный result |
| Неизвестный `message_type` | Закрыть соединение и записать protocol error |
| Payload короче обязательных полей | Закрыть соединение |
| Неверная длина, переполнение или trailing bytes | Закрыть соединение |
| Неверное число FD | Закрыть соединение и закрыть полученные FD |
| Чужой или уже уничтоженный объект | Вернуть `CORE_NOT_FOUND` или `CORE_PERMISSION_DENIED` |
| Переполнена исходящая очередь клиента | Отключить медленного клиента без блокировки сервиса |

Невалидные payload, содержимое строк, input data и пиксели не записываются в
лог. Допустимо журналировать endpoint, `message_type`, размер payload,
`ErrorCode` и факт разрыва соединения.

## Требования к специализированному протоколу

Документ каждого GUI endpoint обязан определить:

1. таблицу `message_type`, направление и тип payload;
2. точную последовательность и ширину предметных полей;
3. пределы строк, массивов, размеров и количества объектов;
4. число ancillary FD для каждого сообщения;
5. допустимые состояния и порядок операций;
6. соответствие request, result и completion event;
7. область уникальности идентификаторов и serial;
8. правила владения и освобождения ресурсов;
9. возможные `ErrorCode`;
10. поведение при disconnect и перезапуске сервиса.

## Ограничения v1

- Только локальный доверенный транспорт через Unix domain sockets.
- Нет согласования диапазона версий отдельным handshake.
- Нет достоверной peer identity в `ipclib`; доступ ограничивается правами
  endpoint и startup secrets привилегированных GUI-клиентов.
- Нет шифрования и сетевого транспорта.
- Нет неизвестных необязательных полей или схемы TLV.
- Ancillary FD требует запланированного расширения `ipclib`.
