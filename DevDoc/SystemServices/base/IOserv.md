## Описание

IOserv — системный сервис физических устройств ввода Linux. Он открывает явно
настроенные устройства /dev/input/event* через inputlib, владеет их жизненным
циклом и публикует клиентам кадры физических событий через локальный IPC.

Сервис не преобразует коды клавиш в текст, не распознаёт жесты и не выбирает
активное окно. Это ответственность appframework и, при его появлении,
windowserv.

## Имя сервиса

| Поле | Значение |
| --- | --- |
| Идентификатор | ioserv |
| Исполняемый файл | IOserv |
| Владелец запуска | initserv |
| IPC endpoint | /run/punos/ioserv.sock |
| Версия протокола | v1 |

## Ответственность и границы

- IOserv открывает устройства из параметров запуска, регистрирует их в event
  loop, читает InputFrame через inputlib и передаёт кадры подписчикам.
- IOserv владеет InputDeviceHandle, состоянием клавиш, кнопок и касаний каждого
  устройства, клиентскими соединениями и подписками.
- После SyncLost сервис сбрасывает собственное состояние устройства и
  передаёт этот кадр всем подходящим подписчикам.
- IOserv не обращается к Linux evdev ABI, read() или ioctl() напрямую и не
  открывает устройство иначе чем через inputlib.
- IOserv не закрывает FD из input_device_get_fd(): им владеет InputDeviceHandle.
- IOserv не преобразует InputEvent.code в Unicode, не меняет координаты, не
  распознаёт жесты и не маршрутизирует ввод в конкретное окно.
- В v1 сервис не выполняет автопоиск устройств: initserv передаёт каждый путь
  отдельным аргументом --device=/dev/input/eventN.

## Зависимости

| Зависимость | Использование |
| --- | --- |
| sys/core | ErrorCode, базовые типы, Bytes и проверка размеров IPC payload |
| sys/memory | Таблица устройств, состояния подписок и временные буферы сериализации |
| sys/string | Пути устройств, IPC endpoint и проверка UTF-8 строк конфигурации |
| special/input | Открытие, чтение и закрытие InputDeviceHandle |
| special/ipc | Endpoint, соединения, кадрирование и исходящие очереди |
| sys/eventloop | Один event loop для endpoint, соединений и устройств |
| logserv | Журналирование запуска, отказов устройств и ошибок протокола |

IOserv не зависит от windowserv, compositorserv или displayserv. Они могут
быть клиентами позже, но не требуются для запуска сервиса.

## Жизненный цикл

### Запуск

| Параметр | Значение |
| --- | --- |
| Готовая зависимость | logserv |
| Параметры | Один или несколько аргументов --device=/dev/input/eventN |
| Успех | Созданы endpoint и event loop; открытые устройства зарегистрированы в event loop |
| Ошибка endpoint или event loop | Завершение с PROCESS_EXIT_INITIALIZATION_FAILED |
| Ошибка одного устройства | Запись в logserv; остальные устройства продолжают открываться |

Сервис переходит в Ready, если endpoint и event loop созданы, даже когда ни
одно устройство не открылось. Это сохраняет возможность диагностики через IPC.

### Остановка и восстановление

При штатной остановке IOserv прекращает приём новых клиентов, удаляет все
источники из event loop, освобождает подписки, закрывает InputDeviceHandle и
закрывает IPC server. Endpoint удаляется только через ipc_server_close().

При EVENT_HANGUP или EVENT_ERROR FD устройства сервис дочитывает устройство до
DeviceLost, отправляет io.device_removed, удаляет FD из event loop и вызывает
input_device_close(). Повторное открытие в v1 выполняется только после
перезапуска IOserv через initserv.

При перезапуске все подписки прекращаются; клиент должен повторно подключиться
и подписаться.

### Состояния сервиса

| Состояние | Допустимые действия | Переходы |
| --- | --- | --- |
| Starting | Создание endpoint, event loop и открытие устройств | Ready, Failed |
| Ready | IPC, чтение устройств и публикация событий | Stopping, Failed |
| Stopping | Освобождение ресурсов | Stopped |
| Failed | Новые операции не принимаются | Завершение процесса |

## Владение ресурсами

| Ресурс | Владелец | Открытие | Освобождение |
| --- | --- | --- | --- |
| IpcServerHandle | IOserv через ipclib | При запуске | При остановке |
| IpcConnectionHandle и подписка | IOserv | При accept | При отключении или остановке |
| InputDeviceHandle | IOserv через inputlib | Для каждого корректного --device | При DeviceLost или остановке |
| FD устройства и IPC | Исходный handle | Вместе с handle | Только закрытием handle |
| InputFrame | IOserv | После FrameReady | Сразу после сериализации через input_frame_destroy |
| Состояние устройства | IOserv | При открытии устройства | При SyncLost, DeviceLost или остановке |

FD, переданные eventloop_add_fd(), не принадлежат event loop и не закрываются
eventloop_remove_source().

## IPC-контракт

### Клиенты и доступ

| Клиент | Разрешённые операции | Проверка доступа |
| --- | --- | --- |
| appframework | io.subscribe, io.unsubscribe | Доверенный системный клиент v1 |
| windowserv | io.subscribe, io.unsubscribe | Доверенный системный клиент будущей UI-конфигурации |

Приложения не подключаются к IOserv напрямую. В ipclib пока нет контракта
получения идентичности peer, поэтому IOserv не может достоверно отличить
произвольный локальный процесс от appframework. До появления такого механизма
endpoint является внутренним, а не публичным API приложений. Это ограничение
безопасности v1, а не реализованная проверка разрешений.

### Формат payload

Каждое сообщение — один кадр ipclib. Тип сообщения задаёт IOserv; все целые
поля payload записываются little-endian. Указатели, строки и внутренние handle
в payload не передаются.

| message_type | Направление | Payload |
| --- | --- | --- |
| 1, io.subscribe | Клиент → сервис | IoSubscribeRequest |
| 2, io.subscribe_result | Сервис → клиент | IoSubscribeResult |
| 3, io.unsubscribe | Клиент → сервис | Пустой |
| 4, io.unsubscribe_result | Сервис → клиент | IoUnsubscribeResult |
| 5, io.input_frame | Сервис → клиент | IoInputFrameEvent |
| 6, io.device_added | Сервис → клиент | IoDeviceEvent |
| 7, io.device_removed | Сервис → клиент | IoDeviceEvent |

### Операции

| Операция | Запрос | Успешный ответ | Назначение |
| --- | --- | --- | --- |
| io.subscribe | IoSubscribeRequest | IoSubscribeResult | Создаёт единственную подписку соединения на подходящие классы устройств |
| io.unsubscribe | Пустой payload | IoUnsubscribeResult | Завершает подписку; закрытие соединения действует так же |

Повторная подписка на одном соединении возвращает CORE_INVALID_STATE. После
успешной отписки клиент вправе подписаться снова.

После успешного io.subscribe сервис отправляет этому клиенту io.device_added
для каждого уже открытого подходящего устройства, и только затем новые
io.input_frame. Поэтому клиент всегда получает метаданные device_id до первого
кадра данного устройства.

### События и подписки

| Событие | Получатели | Данные | Когда отправляется |
| --- | --- | --- | --- |
| io.device_added | Подходящие активные подписки | IoDeviceEvent | Устройство успешно открыто |
| io.device_removed | Подходящие активные подписки | IoDeviceEvent | Получен DeviceLost |
| io.input_frame | Подходящие активные подписки | IoInputFrameEvent | input_device_read_frame вернул FrameReady |

Обычный IoInputFrameEvent сохраняет порядок InputFrame и завершается
SyncReport. Кадр из единственного SyncLost передаётся клиентам после очистки
состояния IOserv. Сервис не синтезирует события отпускания.

Если исходящая очередь ipclib медленного клиента переполнена, IOserv закрывает
только это соединение. Event loop и чтение устройств не блокируются.

### Типы сообщений

| Тип | Поля | Ограничения | Назначение |
| --- | --- | --- | --- |
| IoSubscribeRequest | u16 protocol_version, u32 device_class_mask | Версия 1; непустая маска INPUT_DEVICE_KEYBOARD, INPUT_DEVICE_POINTER, INPUT_DEVICE_TOUCH | Параметры подписки |
| IoSubscribeResult | ErrorCode error | CORE_OK при успехе | Результат подписки |
| IoUnsubscribeResult | ErrorCode error | CORE_OK при успехе | Результат отписки |
| IoDeviceEvent | u64 device_id, u16 bus, u16 vendor, u16 product, u16 version, u32 classes | device_id уникален, пока устройство открыто | Метаданные устройства |
| IoInputFrameEvent | u64 device_id, u64 sequence, u16 event_count, IoInputEvent[event_count] | 1 <= event_count <= INPUT_FRAME_MAX_EVENTS; sequence возрастает для одного устройства | Кадр физических событий |
| IoInputEvent | u8 kind, u16 code, i32 value | kind соответствует InputEventKind; code и value не изменены | Сериализованное InputEvent |

Значения IoInputEvent.kind: 1 = Key, 2 = RelativeAxis, 3 = AbsoluteAxis,
4 = SyncReport, 5 = SyncLost, 6 = Raw.

## Контракты

1. Ошибки ответов подписки и отписки передаются как ErrorCode из libcore;
   CORE_OK — единственный успешный код.
2. Каждый InputDeviceHandle принадлежит потоку-владельцу event loop;
   одновременные обращения к нему не допускаются.
3. При EVENT_READABLE сервис вызывает input_device_read_frame до NoFrame. При
   EVENT_HANGUP или EVENT_ERROR он дочитывает устройство до DeviceLost и затем
   закрывает handle.
4. InputFrame сериализуется до input_frame_destroy. Память кадра не передаётся
   клиенту и освобождается ровно один раз.
5. code и value передаются без преобразования. Текстовые, жестовые и оконные
   события сервис не создаёт.
6. Состояние клавиш, кнопок и касаний хранится отдельно для каждого устройства
   и сбрасывается при SyncLost и DeviceLost.
7. Для одного IPC-соединения допускается только одна подписка. Отключение
   клиента удаляет её без дополнительного сообщения.
8. Все socket и device операции неблокирующие; рабочие потоки и блокирующее
   ожидание в v1 отсутствуют.
9. Endpoint и соединения принадлежат ipclib. IOserv не закрывает их FD
   напрямую и перед штатным закрытием пытается вызвать ipc_connection_flush.

## Потоковая модель и асинхронность

IOserv v1 однопоточный. Один поток создаёт и владеет event loop,
IpcServerHandle, всеми IpcConnectionHandle и InputDeviceHandle.

При EVENT_READABLE endpoint принимает подключения до CORE_WOULD_BLOCK. Для
клиентского соединения сервис читает сообщения до NoMessage; при
EVENT_WRITABLE вызывает ipc_connection_flush. Обработчик устройства читает
кадры до NoFrame. Mutex, рабочие потоки и межпоточные очереди отсутствуют.

## Конфигурация и постоянные данные

| Данные | Источник | Владелец | Действие при ошибке |
| --- | --- | --- | --- |
| Список устройств | Аргументы --device, заданные initserv | initserv | Ошибка пути логируется; остальные устройства запускаются |
| Состояние устройств и подписок | Только память процесса | IOserv | Теряется при перезапуске; клиент подписывается заново |

Постоянные файлы, автопоиск и восстановление состояния между перезапусками в
v1 отсутствуют.

## Логирование и наблюдаемость

В logserv отправляются записи о запуске и остановке; открытии, отказе и
отключении устройства; SyncLost; ошибке протокола; отклонённом запросе;
переполнении очереди и отключении медленного клиента.

Журнал не содержит последовательности нажатых клавиш, координаты касаний и
иные пользовательские события ввода.

## Ошибки

| ErrorCode | Когда возвращается клиенту |
| --- | --- |
| CORE_INVALID_ARGUMENT | Payload неверного размера, пустая маска классов или неизвестный message_type |
| CORE_INVALID_STATE | Повторная подписка или отписка без подписки |
| CORE_UNSUPPORTED | Неподдерживаемая версия протокола или класс устройства |
| CORE_OUT_OF_MEMORY | Нельзя создать состояние подключения или поставить ответ в очередь |
| CORE_IO_ERROR | Некорректный IPC-кадр или ошибка IPC, не позволяющая продолжить соединение |

Ошибки открытия и отказа устройства не являются ответом на подписку: они
журналируются, а DeviceLost передаётся событием io.device_removed.

## Ограничения версии

- Устройства задаются только аргументами --device; udev, автопоиск и повторное
  открытие после DeviceLost отсутствуют.
- Нет достоверной аутентификации IPC-клиента, поскольку ipclib ещё не
  предоставляет peer identity. Endpoint только для доверенных компонентов.
- Нет раскладки клавиатуры, преобразования в текст, жестов, калибровки касаний
  и маршрутизации в активное окно.
- Нет передачи FD, shared memory и обратного управления устройством клиентом.
- Медленный клиент отключается при переполнении очереди; он сам выполняет
  повторное подключение и подписку.
