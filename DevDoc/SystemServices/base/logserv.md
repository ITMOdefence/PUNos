## Описание

logserv — системный сервис структурированного журналирования. Он принимает
записи от доверенных системных компонентов по локальному IPC, назначает им
время, ограничивает очередь и сохраняет записи последовательно через loglib.

Сервис является единственным владельцем текущего журнала. Клиенты не открывают
файл журнала и не используют loglib напрямую.

## Имя сервиса

| Поле | Значение |
| --- | --- |
| Идентификатор | logserv |
| Исполняемый файл | logserv |
| Владелец запуска | initserv |
| IPC endpoint | /run/punos/logserv.sock |
| Версия протокола | v1 |

## Ответственность и границы

- logserv принимает, проверяет и упорядочивает записи, назначает timestamp и
  выбирает момент flush.
- logserv владеет LogStoreHandle, очередью записей и рабочим потоком записи.
- logserv не предоставляет клиентам FileHandle, LogStoreHandle или путь
  текущего файла для прямой записи.
- logserv не выполняет файловый I/O в IPC event loop.
- logserv не изменяет severity, component или текст корректно принятой записи.
- В v1 logserv не предоставляет поиск и чтение истории по IPC; эти возможности
  loglib зарезервированы для будущего административного API.

## Зависимости

| Зависимость | Использование |
| --- | --- |
| special/ipc | Endpoint, соединения, сообщения и исходящие очереди |
| special/log | Открытие, append, flush и закрытие LogStoreHandle |
| sys/event | IPC event loop и пробуждение потока-владельца |
| sys/thread | Создание, join и идентификатор единственного потока записи |
| sys/sync | Mutex, condition variable и сигнал остановки очереди |
| sys/time | Получение WallClockTime при принятии записи |
| sys/process | Тип ProcessId в сохранённой записи |

logserv не зависит от других System Services. Это позволяет initserv запускать
его первым; собственные диагностические записи после открытия LogStoreHandle
logserv добавляет напрямую в свою очередь, а не через собственный IPC endpoint.

## Жизненный цикл

### Запуск

| Параметр | Значение |
| --- | --- |
| Готовые сервисы до запуска | Нет |
| Аргумент | --log-path=/var/log/punos/system.log |
| Успех | Открыт LogStoreHandle, создан поток записи, создан endpoint и event loop |
| Ошибка LogStoreHandle, потока, endpoint или event loop | Завершение с PROCESS_EXIT_INITIALIZATION_FAILED |

Путь журнала передаёт initserv. Каталог должен существовать до запуска:
logserv не создаёт каталоги в v1.

### Остановка и восстановление

При штатной остановке сервис перестаёт принимать подключения, закрывает
подписанные IPC-соединения после попытки передать поставленные ответы, запрещает
добавление новых записей в очередь и ждёт её опустошения. Поток записи вызывает
log_store_flush, log_store_close и завершается; основной поток делает join,
закрывает endpoint и event loop.

При ошибке log_store_append или flush поток записи отмечает хранилище
как Failed, прекращает приём новых записей и запрашивает завершение процесса.
initserv решает, перезапускать ли logserv. Неполный последний кадр после
аварийного завершения является допустимым состоянием loglib; восстановление
или замена файла определяется будущей политикой logserv.

### Состояния сервиса

| Состояние | Допустимые действия | Переходы |
| --- | --- | --- |
| Starting | Открытие хранилища, создание потока, endpoint и event loop | Ready, Failed |
| Ready | Приём, валидация и постановка записей в очередь | Stopping, Failed |
| Stopping | Дренирование очереди, flush и освобождение ресурсов | Stopped |
| Failed | Новые записи не принимаются | Завершение процесса |

## Владение ресурсами

| Ресурс | Владелец | Открытие | Освобождение |
| --- | --- | --- | --- |
| LogStoreHandle | Только поток записи logserv | При запуске | После дренирования очереди |
| IpcServerHandle | Основной IPC-поток | При запуске | При остановке |
| IpcConnectionHandle | Основной IPC-поток | При accept | При отключении или остановке |
| Очередь записей и копии строк | logserv | При принятии записи | После append либо при остановке |
| Mutex и condition variable очереди | logserv | При запуске | После join потока записи |

LogStoreHandle никогда не передаётся IPC-потоку. Payload сообщения копируется
в очередь до ipc_message_destroy; затем worker формирует LogRecordInput,
вызывает log_store_append и освобождает копии строк.

## IPC-контракт

### Клиенты и доступ

| Клиент | Операция | Проверка доступа |
| --- | --- | --- |
| initserv и System Services | log.submit | Доверенный внутренний клиент v1 |
| appframework | log.submit от имени приложения | Доверенный внутренний клиент v1 |

Приложения не подключаются к logserv напрямую. ipclib пока не предоставляет
контракт peer identity, поэтому source_process_id и source_thread_id в запросе
не могут быть проверены по ядру: в v1 это заявленные клиентом значения. Endpoint
предназначен только для доверенных системных компонентов.

### Формат payload

Каждое сообщение — один кадр ipclib. Все целые поля payload little-endian;
строки кодируются UTF-8 без NUL и без указателей.

| message_type | Направление | Payload |
| --- | --- | --- |
| 1, log.submit | Клиент → сервис | LogSubmitRequest |
| 2, log.submit_result | Сервис → клиент | LogSubmitResult |

### Операции

| Операция | Запрос | Успешный ответ | Назначение |
| --- | --- | --- | --- |
| log.submit | LogSubmitRequest | LogSubmitResult | Проверяет запись, назначает timestamp и ставит копию в очередь |

CORE_OK в LogSubmitResult означает, что запись принята в память ограниченной
очереди. Он не означает, что worker уже вызвал log_store_append или что данные
были сохранены через fsync.

### Типы сообщений

| Тип | Поля | Ограничения | Назначение |
| --- | --- | --- | --- |
| LogSubmitRequest | u16 protocol_version, i32 source_process_id, i32 source_thread_id, u8 severity, u16 component_length, u32 message_length, u8 component[], u8 message[] | Версия 1; PID и TID положительные; severity из LogSeverity; component не более LOG_COMPONENT_MAX_LENGTH; message не более LOG_MESSAGE_MAX_LENGTH | Одна запись клиента |
| LogSubmitResult | ErrorCode error | CORE_OK означает принятие в очередь | Результат обработки запроса |

Logserv сохраняет source_process_id и source_thread_id как process_id и
thread_id LogRecordInput. Timestamp получает сам logserv после успешной
валидации LogSubmitRequest.

## Контракты

1. Ошибка в LogSubmitResult — ErrorCode из libcore; CORE_OK является единственным
   успешным кодом.
2. Основной IPC-поток не вызывает log_store_append, log_store_flush,
   log_reader_next и файловые операции.
3. Только поток записи создаёт, использует и закрывает LogStoreHandle.
4. Очередь сохраняет порядок успешно принятых LogSubmitRequest. Поток записи
   передаёт их в log_store_append в том же порядке.
5. Строки component и message копируются до ответа клиенту и действительны для
   loglib только на время одного вызова log_store_append.
6. Очередь ограничена 4096 записями и 4194304 байтами суммарных строк. При
   превышении любого лимита log.submit возвращает CORE_WOULD_BLOCK без записи.
7. Ошибка записи переводит сервис в Failed. Он не подтверждает новые записи
   как принятые и не скрывает потерю данных повторными попытками в event loop.
8. При отключении клиента уже принятая запись остаётся в очереди и будет
   обработана; неполный IPC-кадр отбрасывается ipclib.
9. Ротация не реализована в v1. LogStoreHandle остаётся связанным с одним
   путём до штатной остановки сервиса.

## Потоковая модель и асинхронность

В v1 есть два нативных потока.

- IPC-поток владеет event loop, IpcServerHandle и всеми IpcConnectionHandle.
  Он принимает сообщения, валидирует их, копирует запись в очередь и отправляет
  LogSubmitResult.
- Поток записи ожидает condition variable, владеет единственным LogStoreHandle,
  последовательно вызывает log_store_append и выполняет flush при штатной
  остановке.

Mutex защищает только очередь и её флаги состояния. Он не удерживается во
время log_store_append, flush или IPC-операций. Поток записи будит
IPC-поток через eventloop_wake только при переходе хранилища в Failed.

## Конфигурация и постоянные данные

| Данные | Источник | Владелец | Действие при ошибке |
| --- | --- | --- | --- |
| Текущий журнал | --log-path от initserv | logserv | Ошибка открытия завершает запуск; ошибка записи завершает сервис |
| Очередь записей | Память процесса | logserv | Незаписанные записи теряются при аварийном завершении |

Периодический flush, ротация, поиск по истории и постоянное хранение очереди
не определены в v1. При штатной остановке flush обязателен.

## Логирование и наблюдаемость

После открытия хранилища logserv записывает в него собственные технические
события: запуск, остановку, переполнение очереди, отказ записи и некорректный
IPC-запрос. До открытия файла и после его отказа долговечное
самологирование недоступно; сервис завершает работу и передаёт состояние
initserv кодом завершения.

Записи приложений и сервисов сохраняются как есть. Logserv не добавляет в
журнал содержимое повреждённого IPC payload.

## Ошибки

| ErrorCode | Когда возвращается клиенту |
| --- | --- |
| CORE_INVALID_ARGUMENT | Неверный размер payload, недопустимый severity, пустой component, неположительный PID или TID |
| CORE_UNSUPPORTED | protocol_version отличается от 1 |
| CORE_OVERFLOW | component, message или полный LogRecord превышает лимиты loglib |
| CORE_WOULD_BLOCK | Очередь logserv заполнена |
| CORE_OUT_OF_MEMORY | Нельзя скопировать запись или создать состояние соединения |
| CORE_IO_ERROR | Некорректный IPC-кадр либо хранилище перешло в Failed |

## Ограничения версии

- Нет чтения и поиска истории через IPC.
- Нет достоверной аутентификации IPC-клиента и проверки заявленных PID/TID.
- Нет гарантии сохранения записи в момент CORE_OK: это подтверждение очереди.
- Нет периодического flush, ротации и политики хранения архивов.
- При аварийном завершении записи, ещё находящиеся в памяти очереди, теряются.
