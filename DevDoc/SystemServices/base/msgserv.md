## Описание

msgserv — системный сервис обмена сообщениями между нативными приложениями.
Он принимает соединения приложений по локальному IPC, подтверждает личность
каждого соединения секретом из environment приложения, рассылает публикации
подписчикам и переносит адресные запросы и ответы между приложениями.

Сервис является единственным посредником обмена. Приложения не открывают
соединения друг к другу и не узнают путей, PID и ELF-файлов собеседника: они
знают только `application_id` и выданный брокером `client_id`.

Ядро в обмене не участвует: msgserv — обычный userspace-процесс, как logserv.
Клиентская сторона протокола живёт в модуле `messaging` библиотеки
appframework; приложения не кодируют кадры сами.

## Имя сервиса

| Поле | Значение |
| --- | --- |
| Идентификатор | msgserv |
| Исполняемый файл | msgserv |
| Владелец запуска | initserv |
| IPC endpoint | /run/punos/msgserv.sock |
| Версия протокола | v1 |

Реализация сервиса живёт в собственном репозитории (`brouk`), как appserv,
initserv и logserv; в PUNos входят эта спецификация, запись в
`PlatformRegistry`, снапшот исходников сервиса и модуль `messaging`
фреймворка.

## Ответственность и границы

- msgserv подтверждает личность соединения, проверяет права, рассылает
  события и переносит запросы и ответы.
- msgserv владеет endpoint'ом, всеми принятыми соединениями, таблицей
  подписок, очередями получателей и таблицей запросов, ждущих ответа.
- msgserv заполняет поля отправителя в `event` и `deliver_request` сам, из
  личности, подтверждённой при `bind`. Эти поля отсутствуют в запросе
  клиента, поэтому отправителя нельзя подделать.
- msgserv не хранит сообщения: доставка at-most-once, без персистентности,
  повторов и подтверждений получателем.
- msgserv не запускает приложения и не доставляет сообщения незапущенному
  адресату: launch-on-demand не входит в v1 и остаётся за appserv.
- msgserv не интерпретирует `payload` и не журналирует его.
- msgserv не выдаёт сведений о других приложениях: подписчик, у которого нет
  права получать topic, просто не попадает в рассылку и не учитывается в
  счётчиках издателя.
- msgserv не является публичным endpoint'ом: `application_id` без совпавшего
  секрета отклоняется.

## Зависимости

| Зависимость | Использование |
| --- | --- |
| sys/core | ErrorCode, Bytes, базовые типы и проверка размеров кадров |
| sys/memory | Состояния соединений, узлы очередей получателей, копии кадров |
| sys/string | UTF-8 `application_id`, topic, method, секрет и IPC endpoint |
| special/ipc | Endpoint, соединения, сообщения и исходящие очереди |
| sys/eventloop | Единственный event loop сервиса |
| sys/time | MonotonicTime для дедлайнов запросов и таймаута `bind` |
| sys/process | Коды завершения процесса |
| Syscall Wrappers | `sigaction()` для SIGTERM и SIGINT |
| logserv | Собственные технические записи через /run/punos/logserv.sock |

msgserv не зависит от appserv и не обращается к нему. Запуск приложений и
обмен сообщениями независимы: брокер узнаёт о приложении только когда то
подключилось и прошло `bind`.

## Жизненный цикл

### Запуск

| Параметр | Значение |
| --- | --- |
| Готовые сервисы до запуска | logserv (необязателен для работы), appserv не требуется |
| Аргументы | Отсутствуют; `argc != 1` даёт PROCESS_EXIT_INVALID_ARGUMENT |
| Успех | Создан event loop, открыт endpoint и зарегистрирован его дескриптор |
| Ошибка event loop, каталога или endpoint | Завершение с PROCESS_EXIT_INITIALIZATION_FAILED |

Последовательность запуска фиксирована:

1. Устанавливаются обработчики SIGTERM и SIGINT.
2. Создаётся event loop.
3. Инициализируется брокер: вкомпилированный каталог прав, пустые таблицы,
   первые значения `client_id` и `correlation_id`.
4. Создаётся клиент logserv. Недоступный logserv не мешает запуску: записи
   просто не уходят.
5. Последним создаётся IPC endpoint.

Поэтому доступный endpoint msgserv означает, что брокер готов принимать
`bind` — как у logserv, где доступный endpoint означает открытое хранилище.
Приложение, запущенное до msgserv, не находит endpoint и повторяет попытку:
переподключение с растущим backoff'ом выполняет модуль `messaging`.

Путь endpoint'а и адрес logserv задаются при сборке сервиса, а не аргументами:
у msgserv нет аргументов командной строки в v1.

### Остановка и восстановление

По SIGTERM или SIGINT сервис выходит из главного цикла, делает одну
неблокирующую попытку отдать уже поставленные в очереди кадры, закрывает
соединения, endpoint и event loop и завершается с PROCESS_EXIT_SUCCESS.
Доставка at-most-once: кадры, не уместившиеся в эту попытку, теряются.

Восстановление состояния после перезапуска не требуется и не выполняется.
Подписки, `client_id` и запросы, ждущие ответа, существуют только в памяти
процесса и исчезают вместе с ним. Приложение узнаёт об этом по разрыву
соединения; модуль `messaging` подключается заново и восстанавливает свои
подписки. `client_id`, выданные до перезапуска, становятся недействительными.

Запись в `PlatformRegistry` — `restart: restart`, `critical: false`: отказ
брокера не останавливает платформу, обмен прекращается до перезапуска.

### Состояния сервиса

| Состояние | Допустимые действия | Переходы |
| --- | --- | --- |
| Starting | Создание event loop, каталога, клиента logserv и endpoint | Ready, Failed |
| Ready | Приём соединений, `bind`, рассылка, запросы, ответы, дедлайны | Stopping, Failed |
| Stopping | Последняя отдача очередей и освобождение ресурсов | Stopped |
| Failed | Ошибка event loop или приёма соединений | Завершение процесса |

## Владение ресурсами

| Ресурс | Владелец | Открытие | Освобождение |
| --- | --- | --- | --- |
| EventLoopHandle | msgserv | При запуске | При остановке |
| IpcServerHandle | msgserv | При запуске | При остановке |
| IpcConnectionHandle клиента | msgserv | При accept | При отключении, нарушении протокола или остановке |
| Подписки и счётчики sequence | msgserv | При `subscribe` | При `unsubscribe`, закрытии соединения или остановке |
| Очередь кадров получателя | msgserv | При постановке кадра | После передачи в ipclib, при переполнении или при закрытии |
| Таблица запросов, ждущих ответа | msgserv | При `request` | При ответе, дедлайне, обрыве адресата или закрытии |
| Соединение с logserv | msgserv | При запуске | При остановке или отказе журнала |

Кадр копируется в очередь получателя до `ipc_message_destroy` принятого
сообщения. Один `publish` превращается в M постановок копии кадра в M
очередей; у каждого получателя своя очередь и свой предел.

## IPC-контракт

### Клиенты и доступ

| Клиент | Операция | Проверка доступа |
| --- | --- | --- |
| appframework от имени приложения | bind | `application_id` из каталога и совпавший секрет |
| Приложение после bind | subscribe, unsubscribe, publish, request, respond | Права этого `application_id` в каталоге |

ipclib v1 не предоставляет контракт peer identity, поэтому брокер не может
получить личность клиента от ядра и не верит содержимому кадра. Приложение
доказывает, кто он, секретом, который appserv передал ему в environment из
`applications.json`; `application_id` без совпавшего секрета отклоняется.

Секрет выводится из солёного хэша `application_id`
(`sha256(salt || 0x00 || application_id)`) при сборке образа. Соль не входит в
образ; одна и та же соль даёт один и тот же образ, поэтому воспроизводимость
initramfs сохраняется.

Модель не защищает от приложения, которое само передаст свой секрет другому
процессу: это осмысленное упрощение v1, пока все приложения каталога считаются
доверенными и установки приложений не существует.

### Формат payload

Каждое сообщение — один кадр ipclib. Все целые поля little-endian; `text` —
`u16` длины и байты UTF-8 без NUL; `blob` — `u32` длины и произвольные байты.
Первое поле каждого запроса клиента — `u16 protocol_version` = 1. У кадров,
которые отправляет брокер незапрошенно, поля версии нет: версию согласовали
при `bind`.

Запрос клиента имеет нечётный `message_type`, ответ на него — тип запроса плюс
один, как в протоколе appserv. Незапрошенные кадры лежат отдельным блоком от
20: клиент обязан отличать их от ответа на свой запрос, и разрыв в нумерации
делает ошибку видимой.

| message_type | Направление | Payload |
| --- | --- | --- |
| 1, bind | Клиент → сервис | `text application_id`, `text secret` |
| 2, bind_result | Сервис → клиент | `u32 error`, при CORE_OK: `text application_id`, `u64 client_id` |
| 3, subscribe | Клиент → сервис | `text topic` |
| 4, subscribe_result | Сервис → клиент | `u32 error` |
| 5, unsubscribe | Клиент → сервис | `text topic` |
| 6, unsubscribe_result | Сервис → клиент | `u32 error` |
| 7, publish | Клиент → сервис | `text topic`, `blob payload` |
| 8, publish_result | Сервис → клиент | `u32 error`, при CORE_OK: `u16 delivered_count`, `u16 dropped_count` |
| 9, request | Клиент → сервис | `u8 target_kind`, при 0: `u64 client_id`, при 1: `text application_id`; затем `text method`, `blob payload` |
| 10, request_result | Сервис → клиент | `u32 error`, при CORE_OK: `u64 correlation_id` |
| 11, respond | Клиент → сервис | `u64 correlation_id`, `u32 status`, `blob payload` |
| 12, respond_result | Сервис → клиент | `u32 error` |
| 20, event | Сервис → клиент, незапрошенное | `u64 sender_client_id`, `text sender_application_id`, `text topic`, `u64 sequence`, `blob payload` |
| 21, deliver_request | Сервис → клиент, незапрошенное | `u64 correlation_id`, `u64 sender_client_id`, `text sender_application_id`, `text method`, `blob payload` |
| 22, deliver_response | Сервис → клиент, незапрошенное | `u64 correlation_id`, `u32 error`, `u32 status`, `blob payload` |

### Операции

| Операция | Запрос | Успешный ответ | Назначение |
| --- | --- | --- | --- |
| bind | bind | bind_result | Подтверждает личность соединения и выдаёт `client_id` |
| subscribe | subscribe | subscribe_result | Добавляет подписку соединения на topic |
| unsubscribe | unsubscribe | unsubscribe_result | Снимает подписку |
| publish | publish | publish_result | Ставит копию кадра `event` в очередь каждого подписчика, имеющего право получать topic |
| request | request | request_result | Ставит `deliver_request` в очередь адресата и запоминает запрос с дедлайном |
| respond | respond | respond_result | Ставит `deliver_response` в очередь отправителя запроса |

CORE_OK в `publish_result` и `request_result` означает, что кадр принят в
память ограниченной очереди получателя. Он не означает, что получатель его
прочитал и обработал.

### Два режима обмена

| Режим | Адрес | Кардинальность | Для чего |
| --- | --- | --- | --- |
| publish → event | topic | Многие-ко-многим | События и уведомления |
| request → response | `client_id` либо `application_id` | 1:1 с корреляцией | Запрос, которому нужен ответ |

Соединение ipclib — AF_UNIX/SOCK_STREAM, то есть всегда 1:1. Многие-ко-многим
живёт в таблице подписок брокера: N приложений держат N обычных соединений,
один `publish` превращается в M постановок кадра в M очередей.

Надёжный адрес запроса — `client_id` из поля отправителя полученного события:
он указывает на конкретное соединение. Адресация по `application_id` —
удобство для случая «подключён ровно один экземпляр»: при нескольких
подключённых она возвращает CORE_ALREADY_EXISTS, при нуле — CORE_NOT_FOUND.
Поэтому приложение объявляет о себе публикацией в topic, а остальные берут его
`client_id` оттуда.

### Лимиты

| Константа | Значение | Почему так |
| --- | --- | --- |
| MSG_APPLICATION_ID_MAX_LENGTH | 64 | Равна APP_ID_MAX_LENGTH appframework |
| MSG_SECRET_MAX_LENGTH | 128 | Секрет из environment приложения |
| MSG_PAYLOAD_MAX_SIZE | 65536 | 64 КиБ × 64 подписчика = 4 МиБ, то есть полный fan-out влезает в IPC_OUTGOING_QUEUE_MAX_SIZE |
| MSG_QUEUE_MAX_RECORDS / MSG_QUEUE_MAX_BYTES | 1024 / 1 МиБ | Своя очередь получателя мягче очереди ipclib, чтобы отказ приходил от брокера, а не из транспорта |
| MSG_CLIENTS_MAX | 64 | Столько же, сколько записей в каталоге приложений |
| MSG_CONNECTIONS_MAX_PER_APPLICATION | 4 | Секрет один на приложение, поэтому число его соединений ограничено явно — иначе одно приложение заняло бы все слоты |
| MSG_TOPIC_MAX_LENGTH | 128 | Длина topic в байтах |
| MSG_METHOD_MAX_LENGTH | 64 | Длина method в байтах |
| MSG_SUBSCRIPTIONS_MAX_PER_CLIENT | 32 | Ограничивает работу на один `publish` |
| MSG_PENDING_MAX_PER_CLIENT | 256 | Как APP_APPS_MAX_PENDING |
| MSG_REQUEST_TIMEOUT_MS | 30000 | Предел жизни запроса без ответа |
| MSG_BIND_TIMEOUT_MS | 5000 | Как таймаут logserv в initserv |

Константы appframework `APP_MSG_*` обязаны совпадать с этими значениями
байт-в-байт.

## Права

Права статические и известны на сборке. Для каждого `application_id` каталог
задаёт четыре списка:

| Список | Что разрешает |
| --- | --- |
| `publish_topics` | Публиковать в эти topic'и |
| `subscribe_topics` | Подписываться на эти topic'и и получать их события |
| `serve_methods` | Принимать `deliver_request` с этими method |
| `call_targets` | Отправлять `request` этим приложениям |

Источник истины — файл прав в репозитории сервиса, а не `PlatformRegistry`: так
не нужно менять ни схему реестра, ни существующие генераторы. Генератор
сервиса читает его вместе с `platform_registry.json` и `applications.json`,
проверяет, что все упомянутые `application_id` существуют, и вкомпилирует
каталог вместе с секретами в исполняемый файл. Нарушение правила — ошибка
сборки, а не предупреждение.

Публикация в topic, где у подписчика нет права получать, не является ошибкой
издателя: такой подписчик не попадает в рассылку и не учитывается в
`delivered_count` и `dropped_count`. Иначе брокер стал бы каналом сведений о
правах и составе других приложений.

Запрос проверяется с двух сторон: адресат должен быть в `call_targets`
отправителя, а `method` — в `serve_methods` адресата.

## Контракты

1. Все ответы содержат ErrorCode из libcore как `u32`; CORE_OK — единственный
   успешный код.
2. Поля отправителя в `event` и `deliver_request` заполняет брокер из личности,
   подтверждённой при `bind`. В запросе клиента этих полей нет.
3. Любое отклонение от формата — усечение, лишний байт, невалидный UTF-8, NUL в
   `text`, неизвестный `message_type`, `protocol_version` не 1, запрос до
   `bind` — закрывает соединение. Брокер не отвечает на кадр, который не
   разобрал: ответ подразумевал бы, что он понял запрос. Повторный `bind`
   разобран и потому получает ответ CORE_INVALID_STATE, а соединение сохраняет
   прежнюю личность.
4. Соединение, не сделавшее `bind` за MSG_BIND_TIMEOUT_MS, закрывается.
5. `client_id` ненулевой, уникален за время жизни процесса и обозначает
   соединение, а не приложение и не экземпляр. Он не переиспользуется.
6. `sequence` считает события одного topic'а для одного соединения и растёт на
   единицу на каждое событие, в том числе на отброшенное из-за переполнения
   очереди. Разрыв в `sequence` — сигнал получателю «я пропустил события, надо
   перечитать состояние».
7. Издатель не получает собственное событие, даже если подписан на этот topic:
   соединение-отправитель исключается из рассылки и не учитывается в счётчиках.
8. Переполнение очереди получателя отбрасывает кадр только для него: остальные
   подписчики получают событие, издатель видит отброшенного в `dropped_count`.
9. Порядок кадров в очереди одного получателя сохраняется.
10. Каждый `request`, принятый с CORE_OK, завершается ровно одним
    `deliver_response`: ответом адресата, CORE_TIMEOUT по
    MSG_REQUEST_TIMEOUT_MS или CORE_NOT_FOUND при обрыве адресата.
11. `respond` принимается только от того соединения, которому брокер доставил
    этот `correlation_id`. Чужой `correlation_id` даёт CORE_PERMISSION_DENIED,
    несуществующий — CORE_NOT_FOUND.
12. В `deliver_response` транспортный `error` и прикладной `status` — разные
    поля; `status` определён только при `error` = CORE_OK.
13. Закрытие соединения снимает его подписки, гасит его запросы, ждущие
    ответа, освобождает его очередь и отправляет CORE_NOT_FOUND тем, кто ждал
    ответа от него.
14. Доставка at-most-once. CORE_OK на `publish` означает «принято в память
    брокера»; персистентности, повторов и подтверждений получателем нет.
15. Отказ в `bind_result` не содержит ни `client_id`, ни подтверждённого
    `application_id`, а «нет такого приложения» и «не тот секрет» не
    различаются в журнале: иначе брокер подсказывал бы подбирающему.
16. Отказ соединения с logserv не останавливает брокера: журнал снимается,
    обслуживание продолжается.

## Потоковая модель и асинхронность

В v1 сервис однопоточный: один event loop, одно ожидание, неблокирующие
соединения. Своих потоков msgserv не создаёт, вся работа делается между двумя
`eventloop_wait`.

Один проход главного цикла:

1. Обслужить соединения, у которых ipclib мог сохранить ещё один кадр.
2. Дождаться событий (ожидание нулевое, если такие кадры остались).
3. Принять новые соединения; разобрать кадры готовых соединений и поставить
   ответы и рассылку в очереди получателей.
4. Истечь дедлайны запросов и таймауты `bind`.
5. Отдать непустые очереди всех клиентов в ipclib.

Пятый шаг отдельный и обязательный: кадр, положенный в очередь чужим
`publish`'ом или истёкшим дедлайном, иначе лежал бы до следующего события на
сокете получателя, которого уровневый epoll не даст — читать там нечего, а
запись брокер для этого соединения ещё не запрашивал.

Таймер нулевого периода не используется: пустое ожидание ограничено 1000 мс,
чего достаточно для дедлайнов в 5 и 30 секунд.

## Конфигурация и постоянные данные

| Данные | Источник | Владелец | Действие при ошибке |
| --- | --- | --- | --- |
| Каталог прав и секретов | Вкомпилирован при сборке сервиса | msgserv | Нарушение правил прав — ошибка сборки |
| Секрет приложения | environment приложения, запись в `applications.json` | appserv передаёт, приложение читает | Нет секрета — приложение не участвует в обмене |
| Endpoint и адрес logserv | Заданы при сборке | msgserv | Недоступный endpoint завершает запуск |
| Подписки, `client_id`, запросы | Память процесса | msgserv | Исчезают при завершении процесса |

Постоянных данных у сервиса нет: файлов он не открывает и ничего не хранит
между запусками.

## Логирование и наблюдаемость

msgserv пишет в logserv только собственные технические события: готовность,
остановку, успешный `bind` и отказ `bind`, отказ соединения выше
MSG_CLIENTS_MAX, отклонённую версию протокола, запрос до `bind`, неизвестный
тип сообщения и таймаут `bind`.

Запись содержит имя события, `application_id` (если личность уже подтверждена),
`client_id` и ErrorCode. В журнал не попадают ни секреты, ни topic'и, ни
method, ни `payload`: иначе брокер стал бы каналом утечки прикладных данных в
общесистемный журнал.

Счётчиков и административного API в v1 нет: состав topic'а и число
подписчиков опросить нельзя.

## Ошибки

| ErrorCode | Когда возвращается клиенту |
| --- | --- |
| CORE_NOT_FOUND | `bind`: нет такого `application_id`. `request`: нет такого `client_id` либо ни одного подключённого экземпляра приложения. `respond`: нет такого `correlation_id`. `deliver_response`: адресат отключился, не ответив |
| CORE_PERMISSION_DENIED | `bind`: секрет не совпал. `subscribe`, `publish`: topic'а нет в правах. `request`: адресата нет в `call_targets` либо метода нет в его `serve_methods`. `respond`: `correlation_id` доставлен другому соединению |
| CORE_OVERFLOW | `bind`: заняты все MSG_CONNECTIONS_MAX_PER_APPLICATION. `subscribe`: упор в MSG_SUBSCRIPTIONS_MAX_PER_CLIENT |
| CORE_ALREADY_EXISTS | `subscribe`: подписка уже есть. `request`: подключено несколько экземпляров адресата |
| CORE_INVALID_STATE | `bind` на соединении, которое уже прошло `bind` |
| CORE_WOULD_BLOCK | `request`: очередь адресата полна либо упор в MSG_PENDING_MAX_PER_CLIENT |
| CORE_TIMEOUT | `deliver_response`: ответ не пришёл за MSG_REQUEST_TIMEOUT_MS |
| CORE_OUT_OF_MEMORY | Нельзя создать состояние соединения или скопировать кадр в очередь |

Нарушение формата кадра не даёт ответа: соединение закрывается.

## Ограничения версии

- Нет персистентности и durability: CORE_OK — подтверждение очереди в памяти.
- Нет доставки незапущенному адресату и launch-on-demand.
- Нет передачи дескрипторов и разделяемой памяти. SCM_RIGHTS в ipclib есть
  (`ipc_connection_send_with_descriptor`, `ipc_connection_receive_with_descriptor`),
  но брокер его не использует: кадры обмена несут только байты. Дескриптор,
  присланный клиентом, закрывает сам ipclib при обычном
  `ipc_connection_receive`, и больше одного входящего за раз не хранится,
  поэтому занять дескрипторы брокера клиент не может.
- Нет wildcard-topic'ов, фильтров по содержимому и приоритетов.
- Нет опроса состава topic'а, числа подписчиков и квот по частоте.
- Нет сетевого транспорта: ipclib поддерживает только AF_UNIX.
- Нет достоверной идентичности IPC-клиента от ядра: личность подтверждается
  секретом приложения, и два экземпляра одного приложения различаются только
  `client_id` соединения, а не устойчивым идентификатором экземпляра.
- Приложение с доступом к своему environment может передать секрет другому
  процессу системы. Модель этого не предотвращает.
