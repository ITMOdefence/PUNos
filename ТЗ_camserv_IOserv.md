# ТЗ: camserv и IOserv (v1)

## 1. Назначение и статус

Документ фиксирует максимально определённое по доступным материалам задание на реализацию и проверку двух System Services. Он не заменяет исходные контракты: при реализации сверять каждый пункт с указанными ниже файлами. Формулировки с пометкой **«открытый вопрос»** не являются разрешением придумать протокол или поведение.

Снимок источников проверен 14.10.2026: локально есть 12 веток `origin/*`; для `camserv.md` и `IOserv.md` во всех ветках тексты одинаковы, кроме старого названия `sys/event` вместо `sys/eventloop` в `origin/system_layer_doc`. Проверка связности локальных Git-объектов прошла. Актуальность удалённых веток на GitHub не подтверждена: терминалу не предоставлены учётные данные для приватного репозитория. Текущие файлы рабочей папки совпадают с `origin/main` для основных документов, но сама рабочая папка находится на пустой ветке `master` с незакоммиченными файлами. Её нельзя считать готовой основой для разработки.

Приоритет: явно заданное поведение `DevDoc/SystemServices` → контракты зависимостей в `DevDoc/SpecialLibs`, `DevDoc/SystemLibs` и публичных заголовках → существующие тесты и реализация как примеры. Код из другой ветки не превращает отсутствующее требование в утверждённый контракт.

## 3. Общие требования к обоим сервисам

**G-01.** Это отдельные нативные процессы Linux x86_64, запускаемые `initserv` из статического реестра; `logserv` должен быть доступен раньше их запуска. Запуск не даёт `initserv` права считать предметный API готовым до появления endpoint.

**G-02.** Каждый сервис владеет одним event loop, IPC-сервером, клиентскими соединениями и своими устройствами в одном потоке. Операции с устройствами и сокетами неблокирующие. Рабочие потоки для этих сервисов не требуются и не предусмотрены v1.

**G-03.** Внешний обмен идёт только через Unix socket и `special/ipc`: 8-байтовый заголовок `u32 payload_size`, `u32 message_type`, затем payload; целые поля little-endian. Максимум payload — 1 048 576 байт; максимум исходящей очереди одного соединения — 4 194 304 байта. Проверять размеры до выделения и копирования. В payload не передавать указатели, внутренние handle и FD устройств.

**G-04.** Endpoint является внутренним интерфейсом доверенных компонентов. В v1 `ipclib` не даёт достоверной идентичности peer: нельзя заявлять, что сервис проверяет личность клиента, или расширять IPC до публичного API приложений.

**G-05.** Полученное через `ipc_connection_receive()` сообщение уничтожать через `ipc_message_destroy()` ровно один раз. `ipc_connection_send()` копирует payload в собственную очередь; сервис отвечает за исходный буфер. FD, переданные в event loop, остаются во владении соответствующего handle. При остановке и отказе не оставлять висячих источников event loop, подписок, соединений и endpoint.

**G-06.** Логировать события, указанные в документах сервисов, через существующий контракт `logserv`/`loglib`; не вводить собственный формат журнала. Ошибки устройства не подменять ошибками ответа на уже выполненную подписку.

**G-07.** Сервисы должны завершаться после `SIGTERM`, поскольку `initserv` при остановке посылает этот сигнал и затем ожидает детей. Точные внутренние детали обработки сигнала брать из существующего сервиса той же ветки, без нового протокола управления.

**G-08.** Продакшн-сборка должна использовать PUNos CRT, Syscall Wrappers и текущие библиотеки проекта, собираться freestanding с теми же проверками ELF (нет неразрешённых символов и `PT_INTERP`), что уже применяются к сервисам. Подмены устройств, ошибки выделения и другой тестовый код не попадут в продакшн ELF.

## 4. camserv: функциональные требования

**C-01. Запуск.** Исполняемый файл `camserv`, endpoint `/run/punos/camserv.sock`. `initserv` передаёт `--device=/dev/videoN`, `--format=<Yuyv|Mjpeg|Nv12>`, `--width=N`, `--height=N`, `--fps=N`. Сервис открывает только этот путь через `camlib`, один раз настраивает и запускает один поток захвата; автопоиска и переключения камеры нет.

**C-02. Порядок и ошибка запуска.** До создания endpoint получить `actual_config` из `camera_configure()` и убедиться, что `actual_config.max_frame_bytes` плюс фиксированные поля `CameraFrameEvent` не превышают `IPC_MESSAGE_MAX_SIZE`; правило действует и для MJPEG. Если камера недоступна, не поддерживает настройки или кадр потенциально не помещается в IPC, endpoint не публикуется, ресурсы освобождаются, причина журналируется, процесс завершается с `PROCESS_EXIT_INITIALIZATION_FAILED` там, где это прямо указано документом. Если после запуска камеры не удалось создать event loop либо endpoint, остановить и закрыть камеру.

**C-03. Владение камерой.** Только `camlib` вызывает операции V4L2; сервис не делает `ioctl`, `mmap`, прямой доступ к FD и не передаёт клиенту `CameraHandle`, FD или MMAP-указатель. При готовности FD читать `camera_dequeue_frame()` до `NoFrame`. Каждый выданный `CameraFrame` скопировать в исходящие IPC-очереди и вызвать `camera_frame_release()` ровно один раз сразу после копирования. Данные кадра не декодировать и не изменять.

**C-04. Клиенты.** На одном IPC-соединении не более одной подписки. `camera.get_info` возвращает состояние и фактическую конфигурацию, `camera.subscribe` создаёт подписку, `camera.unsubscribe` удаляет её. Повторная подписка и отписка без подписки дают `CORE_INVALID_STATE`. После успешной подписки клиент должен получить `camera.ready` до первого `camera.frame`; каждый кадр идёт активным подписчикам с исходными байтами, `sequence` и `monotonic_timestamp_ns`.

**C-05. Размер и медленные клиенты.** Если драйвер дал кадр больше `actual_config.max_frame_bytes` или лимита IPC, его не отправлять никому; записать ошибку, освободить кадр, продолжить захват. Если переполнилась очередь отдельного клиента, закрыть только его соединение; другие клиенты и поток камеры продолжают работать.

**C-06. Потеря устройства.** При `EVENT_HANGUP`/`EVENT_ERROR` дочитать до `DeviceLost`, отправить `camera.device_lost` активным подписчикам, закрыть камеру и завершить процесс. `initserv` перезапускает процесс по политике реестра; старые подписки не восстанавливаются. На штатной остановке перестать принимать клиентов, удалить источники event loop, освободить подписки, вызвать `camera_stop()`, затем `camera_close()` и закрыть IPC-сервер.

**C-07. Границы v1.** Нет изменения формата на лету, нескольких камер, декодирования MJPEG, изменения размера, фильтров, записи фото или видео, shared memory и передачи FD. Логировать запуск с фактической конфигурацией, остановку, отказ камеры и ошибки протокола.

### 4.1. Известная часть IPC camserv

| Сообщение | Подтверждённые поля/свойства |
| --- | --- |
| `camera.get_info` | Запрос назван `CameraGetInfoRequest`, но поля не определены; ответ: `ErrorCode error`, `u8 state`, `CameraStreamConfig config`; config определена только для состояния Streaming |
| `camera.subscribe` | Запрос: `u16 protocol_version`, допустима версия 1; ответ: `ErrorCode error` |
| `camera.unsubscribe` | Пустой запрос; ответ: `ErrorCode error` |
| `camera.ready` | Фактическая `CameraStreamConfig` |
| `camera.frame` | `u64 sequence`, `u64 monotonic_timestamp_ns`, `u32 data_size`, затем `data_size` исходных байтов |
| `camera.device_lost` | `ErrorCode reason` |

**Нельзя считать установленным**, что `CameraStreamConfig` передаётся как 20 байт структуры C, что `CameraPixelFormat` имеет в IPC значения `0/1/2` из ABI библиотеки, либо что сообщения камеры получают номера `1, 2, …`. Эти сведения в контракте `camserv` отсутствуют. См. открытые вопросы B-01–B-04.

## 5. IOserv: функциональные требования

**I-01. Запуск.** Исполняемый файл в документации назван `IOserv`, endpoint `/run/punos/ioserv.sock`. `initserv` передаёт один или несколько аргументов `--device=/dev/input/eventN`; автопоиска нет. Каждый путь открывается через `inputlib`, его FD регистрируется в event loop. Отказ отдельного устройства журналируется, остальные открываются. Сервис становится Ready при созданном endpoint и event loop, даже если не открылось ни одного устройства.

**I-02. Устройства и кадры.** Для каждого открытого устройства хранить полученные `InputDeviceInfo`, состояние клавиш, кнопок и касаний, собственные `device_id` и возрастающий `sequence`. При `EVENT_READABLE` читать `input_device_read_frame()` до `NoFrame`. Передавать кадр как атомарную последовательность событий в исходном порядке; `code` и `value` не менять. После сериализации вызвать `input_frame_destroy()` ровно один раз. Не читать evdev напрямую и не закрывать FD отдельно от `InputDeviceHandle`.

**I-03. SyncLost.** Кадр из единственного `SyncLost` передать подходящим подписчикам после сброса локального состояния данного устройства. Не синтезировать отпускания клавиш/кнопок и не изменять состояние других устройств. Обычный кадр заканчивается `SyncReport`.

**I-04. Подписка и события.** На одно соединение допускается одна подписка с непустой маской классов клавиатуры, указателя и/или касания. Повторная подписка даёт `CORE_INVALID_STATE`; после успешной отписки допускается новая. При подписке послать `io.device_added` для каждого уже открытого подходящего устройства до первого нового `io.input_frame` этого устройства. При открытии устройства событие `device_added` идёт подходящим активным подписчикам. Подписчики получают только подходящие их маске устройства. При отключении клиента подписка удаляется без ответа.

**I-05. Потеря устройства.** При `EVENT_HANGUP`/`EVENT_ERROR` дочитать до `DeviceLost`, отправить `io.device_removed` подходящим подписчикам, удалить источник event loop и закрыть `InputDeviceHandle`; другие устройства и клиенты продолжают работать. Повторно открыть устройство разрешено только после перезапуска всего `IOserv` через `initserv`.

**I-06. Медленный клиент и завершение.** Переполнение очереди одного клиента закрывает только его соединение. На остановке перестать принимать клиентов, удалить источники, освободить подписки и устройства, перед закрытием соединений попытаться выполнить `ipc_connection_flush()`, закрыть сервер через `ipc_server_close()`. После перезапуска клиенты подключаются и подписываются заново.

**I-07. Границы v1.** Не превращать физические коды клавиш в текст, не изменять координаты, не распознавать жесты, не выбирать окно и не открывать публичный IPC для приложений. Логировать запуск/остановку, открытие/отказ/отключение устройства, SyncLost, ошибки протокола, отклонённые запросы и отключение медленного клиента. В журнале не должно быть самих нажатий, координат касаний и других пользовательских событий ввода.

### 5.1. IPC IOserv: установленная часть

Все поля payload сериализуются по порядку таблицы, little-endian. Для `IoInputEvent.kind` использовать значения **1–6 из протокола**, а не внутренние значения **0–5** `InputEventKind` в C API `inputlib`.

| `message_type` | Направление | Payload и длина по указанным полям |
| --- | --- | --- |
| `1` `io.subscribe` | клиент → сервис | `u16 protocol_version=1`, `u32 device_class_mask`; 6 байт |
| `2` `io.subscribe_result` | сервис → клиент | `ErrorCode error`; 4 байта при кодировании как `u32` |
| `3` `io.unsubscribe` | клиент → сервис | пустой payload |
| `4` `io.unsubscribe_result` | сервис → клиент | `ErrorCode error`; 4 байта при кодировании как `u32` |
| `5` `io.input_frame` | сервис → клиент | `u64 device_id`, `u64 sequence`, `u16 event_count`, затем `event_count` элементов `u8 kind`, `u16 code`, `i32 value`; 18 + 7×N байт, `1 ≤ N ≤ 256` |
| `6` `io.device_added` | сервис → клиент | `u64 device_id`, четыре `u16` (`bus`, `vendor`, `product`, `version`), `u32 classes`; 20 байт |
| `7` `io.device_removed` | сервис → клиент | тот же `IoDeviceEvent`, 20 байт |

Маски классов из `inputlib`: `KEYBOARD=1`, `POINTER=2`, `TOUCH=4`. `device_id` уникален, пока устройство открыто; фиксированное начальное значение или глобальная уникальность после закрытия не обещаны. `sequence` возрастает отдельно для каждого устройства; фиксированное начальное значение не обещано. Ветка `origin/GUI-windowserv` подтверждает указанные длины и значения для своего клиента, но её дополнительные ограничения (например, `device_id != 0`) не следует автоматически переносить в нормативное ТЗ `IOserv`.

Ошибки ответа: неверный размер payload и пустая маска → `CORE_INVALID_ARGUMENT`; повторная подписка/отписка без подписки → `CORE_INVALID_STATE`; неподдерживаемая версия или класс → `CORE_UNSUPPORTED`. Неизвестный `message_type` назван причиной `CORE_INVALID_ARGUMENT`, но формат ответа для него не задан: см. B-05.

**Пример для независимого wire-теста.** Подписка на клавиатуру и касание с версией 1 имеет маску `1 | 4 = 5`. Полный IPC-кадр в hex: `06 00 00 00` (размер payload), `01 00 00 00` (тип `io.subscribe`), `01 00 05 00 00 00` (версия и маска). Для успешного ответа ожидается кадр `04 00 00 00 02 00 00 00 00 00 00 00`. Это пример установленного протокола IOserv; аналогичный полный байтовый пример для `camserv` до B-01/B-02 составить нельзя.

## 6. Интеграция и состав работы

1. Для реализации выбрать рабочую ветку с уже существующей инфраструктурой `System/SystemServices`. Если к моменту начала работы она есть в `origin/main`, использовать её; иначе базироваться на `origin/feat/initserv-logserv` и явно указать это в результате. Создать отдельную ветку с префиксом `codex/`; текущие незакоммиченные файлы на пустом `master` не трогать и не удалять. Неподтверждённые удалённые изменения перепроверить доступным способом перед выбором основы.
2. Добавить два сервиса в структуру `System/SystemServices/` и её сборку, используя соглашения реализованных `appserv`, `logserv`, `initserv`. Набор конкретных исходных файлов определить по минимально необходимому разделению: код сервиса, код сериализации/десериализации, тесты и правила сборки. Не переносить тестовые подмены в продакшн.
3. Добавить сервисы в статический реестр `initserv` с точными аргументами запуска только для реально предусмотренной конфигурации; не придумывать путь к устройству, формат камеры, размеры или FPS для default production-конфигурации. Согласовать регистр имени `IOserv`/`ioserv` до фиксации записи реестра (B-06). Обеспечить наличие исполняемых файлов и необходимых каталогов в initramfs при включённых сервисах. Сборка образа должна оставаться воспроизводимой.
4. Если оборудование не задано, сервисы не следует принудительно включать в стандартный образ с вымышленными `/dev/*`. Проверять исполняемые файлы и интеграцию на тестовом реестре и подменных устройствах; возможность включения в штатный реестр должна быть продемонстрирована проверкой сборки/запуска с явно заданной конфигурацией.
5. Не менять поведение других System Services и библиотек сверх необходимой интеграции. Обновить CI так, чтобы новые проверки выполнялись автоматически и старые проверки сохранялись.

## 7. Проверки и критерии приёмки

Каждый пункт ниже требует автоматизированной проверки и понятного сообщения об ошибке. Проверять наблюдаемое поведение через публичные API и IPC; внутренние счётчики и подмены использовать только для проверки владения ресурсами и отказов. Для устройств использовать управляемые фейки `camlib`/`inputlib` либо их нижних зависимостей по образцу существующих тестов, чтобы результат не зависел от физической камеры и клавиатуры. Дополнить настоящими процессами и Unix sockets там, где проверяются границы IPC и завершение.

| ID | Обязательный сценарий | Наблюдаемый результат |
| --- | --- | --- |
| T-01 | Сборка обоих сервисов и ABI/wire тесты | ELF без `PT_INTERP` и неразрешённых символов; точные типы, размеры, endian и пределы сообщений проверены независимыми ожидаемыми байтами |
| T-02 | Корректный запуск camserv | Только переданное устройство открыто, требуемые формат/размер/FPS выбраны, фактическая конфигурация опубликована после запуска |
| T-03 | Ошибки камеры/конфигурации/endpoint/event loop | Нет опубликованного endpoint после ошибки; ресурсы закрыты ровно один раз; код завершения и журнал отвечают определённому контракту |
| T-04 | Граничный размер кадра | Ровно допустимый размер проходит; `max_frame_bytes` выше лимита отклоняется до endpoint; кадр больше допустимого отбрасывается и освобождается |
| T-05 | Подписки камеры и два клиента | Ответы, `ready` перед кадром, одинаковые исходные байты и метаданные у обоих; повторная подписка и отписка без неё дают ошибки; отключение удаляет подписку |
| T-06 | Несколько кадров камеры, `NoFrame`, `DeviceLost` | Порядок сохранён, каждый кадр освобождён один раз, потеря камеры уведомляет активных клиентов и завершает сервис; после перезапуска подписки нет |
| T-07 | Медленный клиент камеры | При переполнении закрыт только он; быстрый клиент и захват продолжаются |
| T-08 | Запуск IOserv с несколькими устройствами, включая отказ одного | Успешные устройства работают; ошибка одного записана в журнал; Ready возможен при нуле открытых устройств |
| T-09 | IOserv: подписка по каждому классу и их комбинации | Для подходящих устройств приходит `device_added` до первого кадра; чужие классы не доставляются; повторная подписка/отписка проверены |
| T-10 | IOserv: обычный кадр и `SyncLost` | Порядок, `code`, `value` и wire `kind=1..6` сохранены; `SyncLost` передан одним событием после сброса состояния только своего устройства; синтетических отпусканий нет |
| T-11 | IOserv: `DeviceLost` одного устройства | `device_removed` содержит его метаданные, handle/источник удалены, остальные устройства продолжают работать; самостоятельного повторного открытия нет |
| T-12 | Медленный клиент IOserv, отключение, новая подписка | Изолированное закрытие медленного клиента; отсутствует старая подписка; повторное подключение работает |
| T-13 | Ошибочные IPC-входы обоих сервисов | Неверные размеры, усечённые кадры, неизвестные/неподдерживаемые значения и переполнения обрабатываются согласно утверждённому протоколу без утечек и остановки других клиентов |
| T-14 | Остановка и перезапуск через initserv | `SIGTERM` приводит к завершению и удалению endpoint; `initserv` освобождает ребёнка и следует политике перезапуска; после рестарта клиент подключается заново |
| T-15 | Журнал IOserv | Есть технические события, но нет кодов нажатий, координат и сырой последовательности пользовательского ввода |
| T-16 | Полная сборка/регрессия | `make -C System/SystemServices check`, проверки библиотек, сборка initramfs и существующий QEMU boot smoke проходят; тестовые фейки не входят в образ |

Проверки T-01, T-05, T-09, T-10, T-13 не должны просто кодировать сообщение и декодировать его тем же кодом: нужны заранее записанные ожидаемые байты/независимый клиент. В частности, ошибка смещения или одинаковая ошибка в encoder и decoder иначе останется невидимой. Реальное оборудование может быть дополнительной ручной проверкой, но не условием воспроизводимых автоматических тестов без отдельного требования.

Исполнитель обязан предъявить таблицу «ID требования → тест → результат», точные команды запуска, их код возврата, вывод CI и список непроверенных случаев. Зелёная сборка сама по себе не доказывает T-02–T-15.

Ориентиры для команд после перехода в правильную feature-ветку: `make -C System/SystemServices check` проверяет сервисы; `make -C System/SpecialLibs check` проверяет их нижние библиотеки; `./System/scripts/build-initramfs.sh` собирает образ; `./System/scripts/check-qemu-boot.sh` запускает автоматический QEMU smoke в сервисной ветке. Последняя команда требует собранного ядра и установленного QEMU, поэтому в CI она надёжнее как приёмочная проверка, чем ручной интерактивный `run-qemu-initramfs.sh`. Для T-16 дополнительно проверить состав образа: при включении сервисов там находятся нужные ELF, а бинарники тестов и фейки в production-образ не попали.

## 8. Порядок выполнения

1. Прочитать источники из раздела 2, проверить актуальные ветки и зафиксировать основу feature-ветки. Отделить факты документации от примеров из кода других веток.
2. Закрыть блокирующие вопросы B-01–B-06 и согласовать противоречие B-07 ниже в документации/согласованном решении. До этого можно готовить независимые части и тестовую инфраструктуру, но нельзя объявлять полный IPC-контракт определённым или считать интеграцию сервисов завершённой.
3. По утверждённому wire-контракту реализовать кодек и негативные тесты с независимыми ожидаемыми байтами.
4. Реализовать `IOserv` и `camserv` по разделам 3–5, сначала жизненный цикл ресурсов и устройства, затем IPC-подписки и события, затем отказные пути.
5. Добавить тесты T-01–T-15 и интеграцию реестра/образа/CI, выполнить T-16. Проверить отсутствие регрессии старых сервисов и библиотек.
6. Предъявить результат: diff в feature-ветке, таблицу требований и тестов, фактический вывод проверок и перечень оставшихся ограничений. Не называть работу завершённой при нерешённых B-01–B-07 или непрошедшей обязательной проверке.

## 9. Открытые вопросы: документация не даёт ответа

Следующее обнаружено после сопоставления документов во всех 12 загруженных ветках. Это не скрытые детали, которые можно взять из `ipclib`: библиотека не определяет семантику сообщений сервисов.

| ID | Что требуется определить для полного ТЗ и тестов | Где виден пробел |
| --- | --- | --- |
| B-01 | Числовые `message_type` всех запросов, ответов и событий `camserv`; направления и допустимые ответы на неизвестный тип | `camserv.md`, 113–139; `ipclib.md`, 49–52 |
| B-02 | Поля/размер `CameraGetInfoRequest`; числовые значения `u8 state`; точный wire-формат `CameraStreamConfig` и значений pixel format; содержимое ответа, когда config «не определена» | `camserv.md`, 115–139; `camera.h` задаёт C ABI, но не IPC |
| B-03 | `ErrorCode reason` события `camera.device_lost`: какой конкретно код передавать при статусе `DeviceLost`, когда `camlib` не возвращает отдельную причину | `camserv.md`, 73–76 и 139; `camlib.md`, описание `camera_dequeue_frame` |
| B-04 | Какой код отдавать за неподдерживаемую версию `camserv`: таблица относит её одновременно к `CORE_INVALID_ARGUMENT` и `CORE_UNSUPPORTED` | `camserv.md`, 191 и 193 |
| B-05 | Каким `message_type` вернуть `CORE_INVALID_ARGUMENT` на неизвестный тип входящего сообщения `IOserv`: тип такого ответа отсутствует | `IOserv.md`, 125–133 и 234 |
| B-06 | Единый `service_id` ввода: `IOserv.md` называет `ioserv`, а `initserv.md` и генератор реестра используют `IOserv`. Не смешивать имя ELF, service id и путь endpoint | `IOserv.md`, 11–19; `initserv.md`, 77–83; `origin/feat/initserv-logserv` |
| B-07 | Целевой клиент ввода при полной интеграции: `IOserv.md` называет `appframework`, но `appframework.md` запрещает прямое подключение; GUI-ветка использует `windowserv`. Серверный IPC можно тестировать независимым клиентом до решения, но нельзя утверждать, что клиентская интеграция выполнена | `IOserv.md`, 104–117; `appframework.md`, 23–31; `origin/GUI-windowserv` |

Не являются блокерами: точное начальное значение `sequence`, способ выдачи `device_id` и наличие физической камеры в CI. Документы задают для них достаточные проверяемые ограничения либо допускают детерминированные фейки. Конкретные device-path, разрешение и FPS для production-реестра должны приходить из конфигурации платформы, а не из догадки исполнителя.
